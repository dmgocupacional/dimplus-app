# Sessão 04/09/2026 — SDK 54 → 57, e por que o projeto tinha sumido do Expo Go

**Estado final:** `main` · **v4.0.0** · commit `1ab156d` · SDK 57 · RN 0.86.3 · React 19.2.3 ·
update publicado no canal `preview` com runtime `exposdk:57.0.0`.

## O sintoma

A aba **Projects** do Expo Go no iPhone do Henrique mostrava *"No projects yet"*. Sem erro, sem
mensagem — o projeto simplesmente não estava lá.

## A causa, e as hipóteses que caíram antes dela

O Settings do Expo Go mostrava **Client Version 57.0.9 / Supported SDK 57.0.0**, contra um
projeto na **SDK 54**. Descasamento de runtime: os updates existiam e o servidor os entregava,
mas eram invisíveis para aquele cliente.

Antes de chegar aí, três hipóteses minhas caíram — todas por eu teorizar antes de medir:

1. *"O projeto foi excluído."* Não: responde pelo ID, e o EAS tinha um build (falho).
2. *"É filtro de conta — o projeto é da org `dimpluss-team` e você está na pessoal."* Não. A
   captura do Settings derrubou.
3. *"O vínculo branch → canal está quebrado."* Não: simulando a requisição que o Expo Go faz
   (`expo-channel-name: preview` + `expo-runtime-version: exposdk:57.0.0`), o servidor respondeu
   **HTTP 200** com o manifesto do update do dia.

## 🩸 A lição que inverte a doc anterior

O `ROADMAP-APP.md` do erp dizia que o teto era *"limite de iOS do device; reinstalar não
resolve"*, e que só trocar de iPhone permitiria subir a SDK. **Está errado.** O teto é a versão
do **app Expo Go**, que se atualiza sozinha pela App Store — e por isso o problema se inverteu
entre 13/07 (Expo Go na 54, projeto na 57) e hoje (Expo Go na 57, projeto na 54).

A Expo **não** distribui versões antigas do Expo Go, então não dá para "voltar" o cliente. Isso é
argumento estrutural a favor de **development build** em vez de Expo Go — que é o mesmo caminho
da publicação nas lojas.

## A migração

Três saltos, um commit por etapa, em `chore/sdk-57` antes de ir para a `main`:

| passo | versões | resultado |
|---|---|---|
| 54 → 55 | RN 0.83.10, React 19.2 | `tsc` verde; `--fix` adicionou config plugin do `expo-image` |
| 55 → 56 | RN 0.85.3, Hermes V1, `expo-router` reescrito | 2 erros de tipo (abaixo) |
| 56 → 57 | RN **0.86.3**, React 19.2.3 | trivial, como a Expo prometeu |

**O 56 é o salto perigoso** — `expo-router` reescrito do zero e desacoplado do React Navigation,
mínimo do iOS para 16.4, Hermes V1 padrão, `@expo/vector-icons` deixa de vir com o `expo`. **As
quatro não atingiram este app:** a superfície de router são seis símbolos (`Stack`, `Tabs`,
`router`, `useRouter`, `useSegments`, `useFocusEffect`), não há import direto de
`@react-navigation`, `reanimated` não é usado no código (só transitivo), e `@expo/vector-icons`
já estava declarado explicitamente no `package.json`.

Validado: `tsc --noEmit` verde, `expo-doctor` **21/21**, e bundle iOS exportado de verdade pelo
Metro (3.6 MB de bytecode Hermes) — este último é a prova de que os imports resolvem, coisa que
o `tsc` não cobre.

### O único ajuste de código: TS2871

O SDK 56 traz **TypeScript 6**, que passou a acusar `This expression is always nullish` em
`historico-agendamentos.tsx` e `meus-agendamentos.tsx`. **É falso positivo**, provado em caso
mínimo: os dois operandos são `string | null`, e a mesma expressão fora da cadeia `??` não
dispara. Corrigido extraindo o lookup de especialidade para uma const nomeada — mesmo
comportamento, em commit de refactor separado do bump (Tidy First).

## Efeito colateral aceito

O runtime publicado passou de `exposdk:54.0.0` para `exposdk:57.0.0`. **Quem tiver o app
instalado com runtime 54 para de receber updates até reinstalar.** A base instalada é o próprio
Henrique, então é indolor hoje.

## Aberto ao fim da sessão

- **O projeto continuou não aparecendo na aba Projects** mesmo depois do update na 57. O servidor
  está provado correto (200 no manifesto), então o que resta é do lado do aparelho: cache do
  Expo Go, ou listagem de projeto privado de organização. Testar pelo link direto
  `exp://u.expo.dev/2147d4ae-6bfc-4c81-b582-1b115af6b830?channel-name=preview&runtime-version=exposdk:57.0.0`,
  que pula a lista.
- **O run do GitHub Actions de 01/09 falhou** e ninguém foi avisado — o canal `preview` ficou
  três dias parado em silêncio. Não investigado. Merece um alerta: publicação que falha calada é
  o mesmo modo de falha do aceite desligado por 4 dias em 28/08.
- **`ios.buildNumber: "1"`** segue no `app.json`. O EAS ignora com versionamento remoto, mas há
  a armadilha do buildNumber remoto contra o app já publicado — ver §PUBLICAÇÃO NAS LOJAS no
  `ROADMAP-APP.md` do erp.
